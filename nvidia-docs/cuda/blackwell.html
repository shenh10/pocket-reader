01 / CUDA FOUNDATIONS
读懂新硬件前，先建立这六个概念

线程不是独立的小 CPU

一个 warp 包含 32 个线程，执行 SIMT 指令。分支条件不一致会让不同路径分批执行；连续线程访问连续地址，才更容易合并内存事务。线程数量增加并不保证吞吐增加。

Block 是资源与协作单位

同一 block 的线程通过 shared memory 交换数据，并用 block barrier 建立执行与内存顺序。不同 block 的普通执行顺序没有保证；不能在普通 kernel 中假设别的 block 已经运行。

片上容量决定并发

每个 block 需要寄存器、shared memory 和线程槽位。任一资源耗尽，都可能限制同一个 SM 上的驻留 block 数。Occupancy 表示驻留 warp 比例，不等于 Tensor Core 利用率；更高不一定更快。

三种“异步”不要混淆

Host 发起的 stream 操作、kernel 内 TMA 搬运、Tensor Core MMA 是不同层次的异步。CPU 提交返回、数据搬运结束和计算完成，是三个不同事件。

性能要沿依赖链测量

用同一 stream 的 CUDA events 测 GPU 时间，并等待结束 event。Host wall time 可用于端到端延迟；只测 launch 调用返回时间，主要量到的是提交开销。

局部优化必须落到应用

一个 GEMM 快一倍，不代表整个训练 step 快一倍。若它只占原时间的 20%，其他部分不变，总体加速只有 1/(0.8+0.2/2)≈1.11 倍。

基础依据：CUDA Programming Guide · CUDA Best Practices Guide。这里的定量模型是教学推导，不是设备实测。

02 / MEMORY
内存层次：容量、复用与可见性是三件事

位置用来做什么需要警惕
Registers线程的地址、标量与临时值。寄存器过多限制驻留；spill 的 local memory 不是另一块高速片上内存，通常由设备内存承载并受缓存影响。
Shared memoryblock 内显式共享 tile，程序员控制复用。bank conflict、同步和容量；不要把 shared-memory 空间等同于所有线程已看到新值。
L1 / L2硬件缓存，减轻下一级访问。缓存命中率依赖访问与工作集；逻辑字节流量不等于 HBM 流量。
Global memory设备可访问的大数组。合并访存、对齐与重复读取；小步长、随机索引和不规则 gather 可能浪费事务。
TMEM特定 Tensor Core 路径的累加器等数据。独立的访问指令、分配与完成规则；不能用普通 load/store 随意操作。

连续不等于无冲突：global memory 中相邻线程读连续地址有利于 coalescing；shared memory 则要看这些地址映射到哪些 bank。例如以 32-bit word 解释、32 个 bank 的简化模型中，线程 t 读 tile[t][0]，行跨度为 32 words 时会落到同一 bank；跨度改为 33 words 可分散。实际数据宽度、广播、向量指令和硬件规则也要一起检查。

Swizzle 解决的是访问布局：TMA 与 MMA 对 SMEM 布局有自己的约束，不能把普通数组加一列 padding 的技巧机械套给 tensor descriptor。CuTe 的 layout 描述逻辑坐标到存储坐标的映射；改变 view 不一定搬动数据，但改变物理排列需要生产者和消费者一致理解。

Cluster / DSM：Hopper 引入的 thread-block cluster 允许受支持设备上多个 block 协作，访问 distributed shared memory。它仍然是多个 block 的 shared-memory 分区，不是无限容量共享池；远端访问前需确保相应 block 已存在，退出前需确保其他 block 不再访问。cluster 同步与 block 同步作用域不同。

03 / EXECUTION
Streams、Events 与 Graphs：优化提交和依赖

通常同一 stream 中操作遵守提交顺序；不同 stream 之间需要显式表达业务依赖。Legacy default stream 可能引入隐式同步，专门的 programmatic dependent launch 也有额外规则，不能将普通 stream 规则机械套用到所有模式。如果计算需要某次拷贝的结果，应显式用 event 等待，或放在同一条 stream 上。多 stream 提供并发机会，不保证硬件一定同时执行。

// 依赖示意：省略创建、销毁和错误检查
cudaMemcpyAsync(device_input, host_input, bytes,
                cudaMemcpyHostToDevice, copy_stream);
cudaEventRecord(input_ready, copy_stream);
cudaStreamWaitEvent(compute_stream, input_ready, 0);
kernel<<<grid, block, 0, compute_stream>>>(device_input);

要可靠地重叠 host↔device 拷贝与计算，通常需要 pinned host memory、非阻塞依赖结构和相应 copy engine 能力。普通 pageable memory 的 staging 行为可能影响异步效果；调用名里有 Async，不代表 host 永远不阻塞。过度使用 pinned memory 也会消耗系统资源。

CUDA Graphs 在哪里有用？

当一轮执行反复提交大量短 kernel，host launch 开销和提交空洞可能占明显比例。Graph 把操作与依赖记录成图，实例化后复用执行，从而减少重复提交成本。它不会让同一个 kernel 的 HBM 自动变快，也不会把真实依赖变成可并行。

看到的现象先尝试如何验证
短 kernel 之间有 host 提交空洞CUDA Graphs、减少同步与重复分配。Nsight Systems 比较图重放前后时间线及端到端延迟。
拷贝与计算可独立但排成串行分 stream、显式 event、合适的 pinned buffer。确认数据依赖正确且时间线上实际重叠。
长 GEMM 本身耗时占绝大多数优化算法、shape、dtype、布局和 kernel。Graph 的额外收益可能很小，测整体收益而非提交耗时。

动态 shape、指针生命周期、图更新与 capture 限制要按 API 规则处理。cudaMallocAsync 则提供 stream-ordered 分配与内存池复用；跨 stream 使用和释放仍需建立正确依赖。它不是消除所有 allocation 开销的魔法。

05 / THE SIX MECHANISMS
六个机制，分别解决什么瓶颈？

① TMEM：累加器搬出寄存器

传统 MMA 的 accumulator 压在寄存器上，会挤占寄存器容量并限制并发。tcgen05 把累加器放进 Tensor Memory，寄存器可留给地址、epilogue 和其他工作。代价是 TMEM 访问也有完成与同步规则，不能当普通 shared memory 用。

② tcgen05.mma：单线程发射

Blackwell 的第五代 Tensor Core MMA 是异步指令，底层由单线程发射；CuTe DSL 的 cute.gemm 调用需由 warp 一致执行，编译器处理线程选举；commit 与 wait/fence 负责建立依赖。不要把“单线程发射”误读成“单线程计算”。

③ TMA：多维搬运交给硬件

TMA 从 Hopper 时代就已引入，并非 Blackwell 独有。它负责 GMEM↔SMEM 的多维 tile 拷贝，线程不再逐元素搬运。它和 pipeline/barrier 配合，把下一块数据搬运与当前块 MMA 重叠。

④ Block Scaling：低比特也能可控

使用 block-scaled 格式时，FP4/FP6/FP8 数据沿 K 方向的每组元素共享 scale factor；这些位宽也存在非 block-scaled 指令形式。计算形式可写成 D=C+(A⊙SFA)·(B⊙SFB)，其中 ⊙ 表示按相应 block 广播 scale 后逐元素相乘，· 表示矩阵乘法。精度与带宽的关键不在“4 bit”本身，而在 scale 的粒度、布局和对齐。

⑤ CTA Group：1SM 或 2SM

CtaGroup.TWO 让相邻 CTA 协作完成更大的 M tile。它改变 tile partition 和 cluster 语义，CUTLASS 会帮你处理大部分切分，但你仍要选择合法的 layout 与 tile。

⑥ Cluster Launch Control

支持 CLC 的设备可让 persistent kernel 取消尚未启动的 block/cluster 工作，取得其索引并自行执行；不能抢走已在运行的工作，缓解不均匀 workload 的尾部空转。它适合动态 tile 调度，不是所有 GEMM 都该启用。

06 / DATAFLOW
一块 tile 的真实旅程

把 kernel 想成三条并行轨道：A/B 负责喂数据，C/D 负责 TMEM 累加器。性能来自重叠，而不是把每一步单独做到极致。

GMEM全局内存中的 A/B tile；尽量连续、对齐。
TMA → SMEM异步多维拷贝；barrier 告诉消费者数据何时到齐。
tcgen05.mmaSMEM descriptor 作为输入，TMEM 保存 accumulator。
TMEM → RMEMepilogue 需要时把结果读回寄存器，不要过早搬回。
GMEM融合 bias/activation/scale 后写回输出。

07 / SYNCHRONIZATION
最危险的错误：把“已提交”当成“已完成”

边界必须建立的事实常见错误
TMA → MMA当前 phase 的数据事务已经完成，且消费者可见。只等生产线程到 barrier，却没正确计入搬运完成条件。
MMA → 复用 SMEM异步 MMA 已消费该输入，生产者才可覆盖缓冲区。MMA 指令发射后立刻覆盖 A/B。
MMA → epilogue通过 tcgen05 completion 路径确认累加完成，再读 TMEM。以为普通 __syncthreads() 自动等完 Tensor Core 操作。
TMEM load/store → 后续操作使用对应的 wait；跨线程传递还要满足相关 fence 与执行同步要求。把 TMEM 指针当成普通 shared-memory 指针。

这些是需要验证的契约，不是一套可以任意拼接的汇编模板。初学优先使用 CUTLASS pipeline abstraction；读具体 kernel 时标记谁生产、谁消费、谁释放每个 stage，再对照 PTX 的 completion 与 proxy 语义。

08 / PIPELINE LAB
把“搬运与计算重叠”变成可见的时间线

假设一个搬运引擎、一个计算引擎、两个输入缓冲区：搬下一块时，计算当前块。每块必须先搬完才能计算，缓冲区也必须等消费者用完才能复用。下图按这些依赖实际排程。

单位为抽象时间单位；不包含 launch、barrier、epilogue、争用与带宽波动。橙色＝搬运，绿色＝计算；编号相同表示同一 tile。

稳态每块耗时逼近 max(搬运时间, 计算时间)，不是两者相加。但首块需要填充、末块需要排空。Tile 只有一块时无法获益；两阶段均衡时，理想加速上限逼近 2 倍。

为什么 stage 不是越多越好？增加缓冲可隐藏更长延迟，却会增加 shared memory 占用，从而减少驻留 block。真正的 TMA/MMA pipeline 还要管理 full/empty barrier、phase、expected transaction bytes，以及消费者是否仍在读当前缓冲区。

09 / ROOFLINE LAB
Tensor Core 更快，为什么你的 kernel 没变快？

算术强度 I＝FLOPs / 从瓶颈内存层搬运的字节数。理想吞吐上界为 min(计算峰值 P, 带宽 B × I)。这里选的是 HBM 层；不能把 HBM 字节、L2 带宽和稀疏峰值混在同一个公式里。

先把 P 加倍，保持 B 和 I 不变：如果仍受带宽限制，理论吞吐不变。再把 I 加倍：复用与融合减少字节流量，才可能提高上界。默认数字只是教学输入，不对应某张 GPU。

GEMM 的复用从哪里来？一个 M×N 输出 tile，在 K 方向每阶段读取 A 的 M×K 和 B 的 K×N 元素，完成约 2MNK FLOPs。只计这两项读取、每元素 s 字节，强度为 2MN/[s(M+N)]。增大 M/N 提高复用，但同时增加片上资源占用；完整 kernel 还要算输出、scale、padding 和重复读取。

10 / PRECISION
FP4 的四个 bit 之外，还藏着什么？

以 dense block-scaled 格式为例：MXFP4 每 32 个元素共享一个 UE8M0 scale，NVFP4 每 16 个元素共享一个 UE4M3 scale。前者的 scale 是幂次形式，后者有尾数，可以更细地调节尺度。完整 NVFP4 量化配方还可能包含额外的张量级缩放；仅存储 4-bit 元素不足以定义完整量化格式。

128 个元素元素数据局部 scale最简存储量
FP16256 B无256 B
MXFP464 B4 × 1 B68 B，即 4.25 bit/element
NVFP464 B8 × 1 B72 B，即 4.5 bit/element

这是仅计 packed 数据与局部 scale 的理想值，尚未计张量级 scale、padding、布局、对齐和中间结果。所以“FP16 换 FP4”并不自动让内存占用或端到端耗时降到四分之一。

为什么 scale 粒度会影响误差？

用一个简化的 E2M1 演示：非负可表示值为 0、0.5、1、1.5、2、3、4、6。若一组元素包含 0.1 和 12，采用最大值 / 6 的简化尺度 s=2，则 0.1/s=0.05 会量化到 0，12/s=6 则可精确表示。若把小值放到另一组并用 s=0.25，0.1/s=0.4 会量化到 0.5，反量化为 0.125。分组降低了大离群值对小值的影响，但增加了 scale 开销。

上述例子只解释尺度与舍入，未实现 NVFP4 的完整量化算法。FP32 accumulator 能减少累加误差，却不能恢复输入量化时已丢失的信息。验证时同时看绝对误差、相对误差与下游模型质量；参考值接近零时，单用相对误差容易误导。

11 / FIRST KERNEL
先读懂“描述硬件”，再读懂 GEMM

# CuTe DSL：描述 Blackwell tcgen05 MMA
import cutlass
import cutlass.cute as cute
from cutlass.cute.nvgpu import tcgen05, OperandMajorMode

op = tcgen05.MmaF16BF16Op(
    cutlass.Float16, cutlass.Float32,
    (128, 256, 16),          # instruction shape M,N,K
    tcgen05.CtaGroup.ONE,
    tcgen05.OperandSource.SMEM,
    OperandMajorMode.K, OperandMajorMode.K,
)
tiled_mma = cute.make_tiled_mma(op)

# 主循环的关键顺序（概念代码）
# 1. TMA: GMEM -> SMEM
# 2. cute.gemm(tiled_mma, acc_tmem, a_smem, b_smem, acc_tmem)
# 3. 等待 tcgen05 完成，再做 TMEM -> RMEM epilogue
读法：这段不是“复制粘贴就能跑”的完整 benchmark，而是把硬件契约显式标出来：输入从哪里来、accumulator 在哪里、MMA 是什么形状、CTA 是单组还是双组。完整 kernel 应使用 CUTLASS 的 builder、合法的 alignment/layout，并在目标 GPU 上编译验证。

Rubin 值得关注的四个变化

更多 TMEM 列

源码把 SM100 的 512 列扩到 SM107 的 576 列，即增加 12.5%。每列 128×32 bit，分别折合 256 KiB 与 288 KiB。这增加容纳 accumulator 的可能性，但 allocator 粒度、合法 tile 和并发约束仍然存在，不能把所有列随意切给任意 CTA。

更大的 SMEM 预算

该快照 CUTLASS 的可用容量常量为 SM100 232448 B（227 KiB）、SM107 334848 B（327 KiB）。这些是库使用的容量预算，不要直接当作硬件物理总容量。它可能允许更多 stage 或更大的输入 tile；是否更快仍取决于 occupancy 与流水线。

B collector reuse

发布说明新增 B operand collector reuse：在适用的 MMA 序列中复用 B 操作数。它针对 Tensor Core 输入路径的重复工作，不等价于 HBM 流量自动下降。应分别看 global/shared 访问与 MMA 的实际瓶颈。

低精度与 softmax 路径

发布说明列出更高吞吐 FP8（MMA_K=64）、FP4（MMA_K=128）、混合精度改进及 softmax 相关加速。MMA_K 是指令的归约粒度，不是应用总 K；更大的指令粒度可能增加小形状 padding，仍需比较端到端收益。

预览支持如何使用：这个版本同时记录了部分 Rubin packed arithmetic 的错误代码生成问题。请固定 toolkit、driver、CUTLASS commit，并对照该版本 Known issues；“编译成功”和“有这个架构选项”都不等于数值正确。这里不把预览支持写成已验证的生产性能。

可复核来源：硬件表、4.8 更新与 Known issues · 架构资源常量 · TMEM 列数。容量换算和性能影响是本页推导，非实测结果。

14 / RUN IT YOURSELF
第一个实验：建立可信的测量习惯

下载完整 bandwidth.cu。这是一个 CUDA C++ 向量加法实验，目的是理解访存、计时与缓存，不是展示 tcgen05。需要 NVIDIA GPU、匹配的驱动和 CUDA Toolkit。当前验证环境为 Mac，无 nvcc；源码已检查，尚未在 GPU 上编译或运行，不提供虚构跑分。

# 在有 NVIDIA GPU 的机器上
nvcc -O3 -std=c++17 -arch=native bandwidth.cu -o bandwidth
./bandwidth 1024
./bandwidth 16777216
./bandwidth 67108864
compute-sanitizer --tool memcheck ./bandwidth 1025

-arch=native 需要支持该选项的 nvcc 和构建机上可见的目标 GPU；若工具链不支持，按 nvcc --list-gpu-code 选择实际设备的目标。最后一组测试会占约 768 MiB 显存和相同量级的 host 内存，分配失败会报错退出。

  1. 先看 correctness：输出的 mismatches 应为 0，退出码为 0。1025 这样的非 block 整数倍用于检查边界。
  2. 再看大小效应：小数组可能主要受启动、提交或缓存影响；大数组更容易暴露数据搬运开销。重复访问同一地址可能命中 L2。
  3. 核对分子：每元素两次 float 读取、一次写入，逻辑流量是 12N bytes。输出的 GB/s 使用十进制，排除 host↔device 拷贝。
  4. 核对分母：同一 stream 的 start/stop event 包围 100 次 launch，再取平均。小 kernel 若因 host 提交形成 GPU 空闲，这些间隙也会计入，不能当作孤立 kernel 的最低延迟。
  5. 用 profiler 解释：先用 Nsight Systems 看提交与空闲，再用 Nsight Compute 看实际内存流量、缓存和吞吐；不要直接把逻辑 GB/s 当成 HBM 测量值。

第二步：从标准库基线走向 Blackwell GEMM

选择一个真实的 M/N/K、batch、dtype 和 layout，先测 cuBLASLt。再用官方 Blackwell collective builder 示例复现同一问题，最后看 窄精度 GEMM 示例。保留示例自带的校验路径；不要跳过 scale 布局后只测耗时。

每次只改一个维度：tile → stage 数 → epilogue 融合 → 数据类型。记录精度误差、资源占用、kernel 时间和端到端时间。若比较 dense GEMM，FLOPs 用 2MNK；不要拿稀疏峰值当分母。

15 / APPLY THE MODEL
把硬件机制放回 LLM 工作负载

Prefill：复用与矩阵计算

较大的 token batch 往往能提供更大的 M 维，适合 Tensor Core 与分块复用。但 attention 的 softmax、mask、布局转换和调度也可能成为瓶颈；不能只拿 GEMM 峰值预测整体 TTFT。

Decode：权重与 KV 搬运

小 batch 下，每次加载的权重被少量 token 使用，算术强度较低。增大 batch、量化、KV 布局与减少不必要搬运常比追逐最大 MMA 更有效。batch 增大后，瓶颈也可能转移。

MoE：形状与不均衡

专家收到的 token 数不同，grouped GEMM 和动态调度可能减少尾部浪费。CLC 只能帮助适配它的 kernel 内任务分配，不能消除跨 GPU all-to-all、专家热点或负载倾斜本身。

不要跨层套结论：TMA 是 GPU 内的数据搬运机制；NVLink/NCCL 面向设备间通信；CUDA Graphs 主要减少重复提交开销。它们可能互补，但不会自动替代彼此。先在时间线上定位实际空闲和数据依赖，再选工具。

三道练习，检验你是否真的懂了

为什么 Blackwell 需要 TMEM？
因为 Tensor Core 的 accumulator 如果长期占寄存器，会提高 register pressure；TMEM 让累加结果有专用片上存储，但你必须把 TMEM 的异步完成与 epilogue 读回纳入流水线。
