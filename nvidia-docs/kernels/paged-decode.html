01先锁定本篇执行路径

分析范围 · FlashInfer 普通 paged decode，use_tensor_cores=False 且非 trtllm-gen，标准 softmax、无 RoPE/特殊 logits transform 的示例。不是对所有 FlashInfer backend 的概括。

一次 decode 为每条请求读取一个 Q。逻辑形状是 Q=[B,Hq,D]、O=[B,Hq,D]；K/V 各自存成 [pages,P,Hkv,D]（NHD）或 [pages,Hkv,P,D]（HND）。页表只改变 token 到物理 cache 的映射，不改变 attention 的数学定义。

plan 根据每个 request 的页数、occupancy 估计和 CUDA Graph 条件决定是否分片，写入 request_indices、kv_tile_indices、o_indptr 等 workspace。它不计算 QK，也不把 KV 内容“规划”成连续数组。run 复用这些计划并提交设备工作；序列/布局变更时须满足 API 的重新规划要求。

02一次页表读取：逻辑 token 18 在哪里？

设 B=1、Hq=32、Hkv=8、D=128、P=16，页表 indptr=[0,3]、indices=[7,2,11]、last_page_len=[5]。有效长度为 (3−1)×16+5=37，最后一页剩余位置不能参与 softmax。

page_iter = indptr[b] + floor(token / P) physical_page = indices[page_iter] entry = token % P offset = physical_page × stride_page + kv_head × stride_h + entry × stride_n + feature

连续 NHD 下 strides 为 (16384,128,1024)。token=18、KV head=3、feature=9 对应 page=2、entry=2，元素 offset=35209，FP16 字节偏移=70418。HND 的 stride_h=P×D、stride_n=D，同一逻辑元素偏移变为 39177。K 与 V 各有基地址；偏移相同并不意味着两者是同一个地址。

03GQA 映射与 128 线程 CTA

对上述 FP16、D=128、G=Hq/Hkv=4 的例子，launch 模板给出 vec_size=max(16/2,128/32)=8，bdx=16，bdy=4，num_threads=128，bdz=2，tile_size_per_bdx=1。

坐标拥有的数据 / 工作具体含义
blockIdx.x一个 planned request × KV chunk通过 request_indices / kv_tile_indices 找回原请求与分片。
blockIdx.y一个 KV head同一个 CTA 中 4 个 Q head 共享它。
threadIdx.x = 0..15head_dim 中连续的 8 个元素16 线程完成一个 QK dot 的维度归约；一个 warp 覆盖两个 y 组。
threadIdx.y = 0..3GQA 中的 Q headqo_head = kv_head × 4 + ty；不能把 ty 当成 KV head。
threadIdx.z = 0..1不同 KV 子块的部分状态循环后 sync_state 合并 z 维的 softmax 状态。

一个迭代处理 1×4×2=8 个 KV token。每个 Q head 对该块维护 FP32 的 m、d、o；Q 的向量片段留在寄存器。设 SMEM stage 数为 S，源码预算为：

2 × S × 1 × 4 × 2 × 128 × 2 B + max(1 × 128 × 8 B, 2 × 4 × 2 × 4 B) = 4096S + 1024 B 若 S=2：9216 B（条件示例，S 由架构 dispatch 决定）

第一项是 K/V 环形缓冲；第二项取地址暂存区与归约暂存区需求的较大值。不能把这个 shared-memory 字节数当成“总 kernel 内存占用”：寄存器、输出、分片 workspace 都是另外的资源。

04cp.async：K 用完即可换下一块，V 还要等

本路径通过普通线程加载与 cp.async 隐藏访存延迟，不使用 Blackwell TMA/tcgen05。预取阶段对 K、V 各提交一个 group；主循环轮流等待和复用同一 stage。

顺序源码动作它建立的事实
1wait_group<2S−1> + block.sync()当前 K 已可读取，CTA 中各线程进入同一消费阶段。
2compute_qk + block.sync()当前 K 已被所有相关线程读完；可以覆盖该 K slot。
3下一块 K 的 pred_load + commit_group发出下一次加载；提交并不表示数据已经完成。
4wait_group<2S−1> + block.sync()当前 V 的异步搬运已满足等待条件。
5update_local_state + block.sync()完成 s×V 累加，释放当前 V slot。
6下一块 V 的 pred_load；stage=(stage+1)%S轮转 buffer；退出循环还要 wait_group<0> 再做块内归约。

删掉 compute 后的块级同步，可能让一部分线程提前覆盖别人还在读的 K/V。只保留最后的 __syncthreads() 也不能替代每轮异步 copy 的完成等待。

05只保存状态，为什么仍能精确合并？

下面用自然指数推导。对已处理区间维护 m=max(s)、l=Σexp(s−m)、u=Σexp(s−m)v。新块最大值为 mᵦ 时：

m′ = max(m, mᵦ) α = exp(m − m′) l′ = αl + Σᵢ exp(sᵢ − m′) u′ = αu + Σᵢ exp(sᵢ − m′)vᵢ O = u / l

FlashInfer 把 score 乘 sm_scale_log2 后使用 exp2；该路径 state.get_lse() 是 base-2 的 m+log2(d)。与本页自然 log 的推导比较时必须换底，不能混用两个库输出的 LSE 单位。源码的 o 在归一化前承载加权和，不能只按字段注释猜它始终是最终输出。

split-KV 每块最终得到 Oⱼ 与 LSEⱼ。正确合并是按分区概率质量加权：

L = maxⱼ LSEⱼ wⱼ = exp(LSEⱼ − L) / Σₖ exp(LSEₖ − L) O = Σⱼ wⱼ Oⱼ （FlashInfer 内部对应 exp2）

检查理解 · 为什么各分片 O 的算术平均不对？

分片长度相同也不保证 softmax 质量相同。一个分片有更大的 logits 时，其 LSE 更大，必须占更高权重。忽略 LSE 会改变概率分布。

06性能判断：拆分解决并行度，也引入归约

单条长度 4096、8 KV heads、D=128、FP16 的 K+V 逻辑读取量为 2×4096×8×128×2=16 MiB。Hq=32 时两次乘加约 4×4096×32×128=67.1 MFLOP，理想逻辑强度约 4 FLOP/B。它没有计入页表、Q/O、workspace 和实际 cache traffic，不能直接作为 HBM 实测。

若只有 B×Hkv=8 个 CTA，长序列可能缺少并行度。拆成 C 个 chunk 可增加独立 CTA，但写/读分片输出、LSE、额外 merge launch 都有成本。batch 大到已有足够 CTA 时，继续 split 不一定划算。
