01先选一个能算清的实例

分析范围 · FlashAttention CuTe DSL 的 FlashAttentionForwardSm100。固定 BF16、D=Dv=128、M=N=128、q_stage=2、1 CTA、TMA KV、固定 Q 长度、不启用 split-KV。它是独立源码案例，不声称 vLLM/SGLang 的 FlashInfer backend 会调用此文件。

入口在 interface.py 构造 SM100 实现，再经 __call__ → kernel → load / mma / softmax_loop / correction_loop / epilogue 分配工作。一个工作 tile 包含两组各 128 行 Q；同一轮 K/V tile 被两组 Q 复用。

算子逻辑 tile输入与累加器位置
QKᵀ[128,128] × [128,128] → [128,128]Q/K 在 SMEM，经描述符供 MMA 读取；S 为 FP32，留在 TMEM。
softmax对每行 128 个 score 更新统计量S 从 TMEM 读入寄存器；P 转为输入 dtype 后写回 TMEM。此时 P 还未最终按全序列行和归一化。
PV[128,128] × [128,128] → [128,128]P 来自 TMEM，V 来自 SMEM，FP32 O 在 TMEM 累加；之后 correction 和 epilogue 处理。

同样的在线 softmax 数学，被拆成了不同硬件单元和 warp 的协作。复杂之处在于 O 必须先重缩放才能接收下一轮 PV，而非单纯让 QK 与 softmax “并行运行”。

Warp 12 负责提交 QK/PV MMA；并不意味着只有它的 32 个线程贡献整块数学结果，Tensor Core 操作具有自己的矩阵和线程组织。Warp 14 发出 Q/K/V 的 TMA，0–7 做 softmax，8–11 重缩放 O，13 存储最终结果，15 在此配置中留空。

03TMEM 的 512 列为什么刚好用满？

本配置 tmem_s_offset=[0,128]，tmem_o_offset=[256,384]，总列数 512。按 128 行 × 512 列 × 4 B 的物理容量计为 256 KiB。列号是 TMEM 地址布局，不是普通指针的线性字节偏移。

S₀
0…127S₁
128…255O₀
256…383O₁
384…511

P 的起点分别是 64 和 192：tmem_p_offset = tmem_s_offset + N/2。BF16 P 利用 S 的存储空间；这不是额外再分配两个 FP32 S 大小的区域。score 已转移到寄存器且相关同步成立后，才可以把这块区域用于 P。row_max/row_sum 的向量暂存同样复用 S 的区域，因此“互不相交的永久数组”不是正确模型。

Q staging = 2 × 128 × 128 × 2 B = 64 KiB O staging = 2 × 128 × 128 × 2 B = 64 KiB 每个 KV stage = max(K tile, V tile) = 32 KiB kv_stage = floor((224 KiB − 128 KiB) / 32 KiB) = 3 名义数据预算 = 224 KiB

这里 K/V 复用 stage 存储，不能给每个 stage 再算一份 K 加一份 V。224 KiB 来自此实现的预算常数，不是 SM100 可用 SMEM 的完整硬件上限；barrier、对齐等还要查看 SharedStorage。D=192、Q/O overlap、uneven KV staging 有单独逻辑，本计算器不覆盖。

04五个握手，决定 buffer 何时能复用

逐条标记生产者、消费者与释放条件，比把全图画成“双缓冲”更有用。下面是依赖关系，不是按真实时钟比例绘制的性能时间线。

通道生产 → 消费必须等待的条件
pipeline_q / pipeline_kvTMA load → MMA当前 slot 的搬运事务完成；MMA 消费后通过对应 UMMA pipeline 释放，才能覆盖。
pipeline_s_p_oMMA → softmax + correction → MMA正向表示 S ready；回程汇合 P ready 和 O rescaled 两个事实。不是普通的“读完 S 就释放”。
pipeline_p_lastsplitsoftmax → MMAP 的尾段已经发布。N=128 时 split_P_arrive=96，先发布前 96 列，再发布剩余 32 列。
softmax statssoftmax → correction新的 acc_scale 可见。correction 将旧 O 乘该缩放因子再交还 MMA。
pipeline_o_acc / epilogueMMA → correction → output末轮 O 已完成，才能最终归一化与输出；跨工作 tile 还要防止覆写上一块仍在读取的 O。

源码主循环借助 MMA 顺序和下一轮 S 的完成建立 O 的先后关系，并没有在每次 PV 后都显式提交一次 O_full；最终排空才走专门完成路径。机械地给所有阶段加同一个 barrier 会丢失这种协议。

检查理解 · 为什么 P 已经 ready，PV 仍可能不能启动？

上一轮 O 可能还没有按新的 row max 重缩放。PV 会继续累加到 O，必须同时等 P 的发布和 correction 对 O 的所有权交还；否则新旧概率尺度不一致。

05描述符不是一个“高级指针”

mma_sm100_desc.py 把 instruction descriptor 与 SMEM descriptor 分开构造。前者描述 MMA 的类型和形状，后者描述操作数如何在 SMEM 中解释；两者都不能用一份普通 C 数组指针替代。

描述符本快照编码的信息容易出错的地方
32-bit instruction descriptorA/B/C format、A/B major、符号、M/N 编码等；由 make_instr_desc 构造。同一字节数据用错格式/major，硬件仍可能执行，但数学含义已经改变。
64-bit SMEM descriptorleading/stride offset、version、layout/swizzle 类型；构造输入是 uint128 的 layout。offset 单位为 16 B，不能直接填元素 stride 或普通 byte stride。
SMEM start address(addr & 0x3FFFF) >> 4。低 4 位被移除；地址必须满足布局与对齐约束。
Canonical layout 检查K-major 与 MN-major 有不同的 shape / stride 合法性检查。仅仅连续、能 TMA 搬运，不代表满足这一 MMA descriptor 的布局要求。

研究一个 layout 时按顺序记录：全局张量 shape/stride → TMA 目标 SMEM layout/swizzle → MMA operand partition → descriptor 字段 → TMEM accumulator layout。只读到“用了 TMA”仍然无法判断访存和计算是否一致。

06可以证伪的三个性能假设

假设测量设计反例可能来自
q_stage=2 能摊薄 K/V 加载固定 head、长度、batch，比较合法 q_stage 配置；记录 kernel 与编译资源。Q/O SMEM 与 TMEM 占用更大、可用 KV stage 更少，可能抵消复用收益。
P 分段发布缩短 MMA 等待在可控实验分支中比较一次发布与当前 96/32 分段；同时检查误差和 barrier 正确性。softmax 不是瓶颈、额外同步成本、不同 N 或 dtype 改变收益。
更多 warp 不代表更多有效算力分析各 warp role 的等待、issue 和寄存器压力；看端到端 attention 时间。MMA、TMA 或 softmax 中任一路饱和，其余 warp 可能只是等待。

先用仓库自己的正确性测试覆盖 causal、varlen、尾块、不同 head dim，再做修改版 benchmark。把 BF16 输出与 FP32 reference 比较；只测单一整齐 shape 很容易漏掉 descriptor 和 masking 问题。
