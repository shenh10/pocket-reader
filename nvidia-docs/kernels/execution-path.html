SGLang 的选择顺序，优先级不能交换

  1. 环境变量存在：只有忽略大小写后的 true 返回真。1 返回假。
  2. 旧版 FlashInfer 兼容函数存在：返回“该 group size 已编译”时走 SIMT，否则选 Tensor Core；这一分支提前返回。
  3. 没有旧函数时：FP8 选 Tensor Core；FP16/BF16 在 GQA ≥ 4 时选 Tensor Core；其他类型返回假。

GQA=Hq/Hkv。例如每 rank 的 Hq=32、Hkv=8，group size=4。若 TP/DCP 改变可见的 head 数，应使用函数真正收到的参数重新计算。这个阈值是此版本的选择策略，不是 Tensor Core 硬件支持的定理。

自测：为什么设置环境变量为 1 后，FP8 也返回 False？

覆盖分支最先执行并直接返回，只比较是否等于字符串 true。它不会继续走 FP8 fallback。实验还提醒：这是选择函数的结果，不保证随意强制出的路径能够成功运行。

03plan 并不等于“自动调参”

在旧 decode wrapper 中，plan 先整理页表、序列长度与 workspace，再选择模块并构造执行元数据；run 把 Q/K/V 和元数据送给模块。JIT 模块缓存、split-KV 计划、Autotuner tactic 缓存分别解决不同问题。

decode.py 分支planrun
backend="trtllm-gen"组织 block tables / KV lengths，取得 TRT-LLM 模块；plan_info 可为 None。构造器将 use_tensor_cores 设为真。进入 Tensor Core 公共参数组，经 cached_module.paged_run 调用对应模块。
use_tensor_cores=True，非 TRT无定制 JIT 时明确调用 get_batch_prefill_module("fa2")；Q 的每请求长度为 1，但复用 prefill 模板。paged_run；“decode API”并不要求底层符号叫 decode。
use_tensor_cores=False，非 TRT无定制 JIT 时取 get_batch_decode_module，规划 split 元数据与临时空间。cached_module.run；本站 Paged decode 案例深入的是这一条。

一组可手算的页表

page_size = 16 indptr = [0, 2, 3] # 请求 0 有两页，请求 1 有一页 indices = [7, 2, 9] # 物理页号，无需连续 last_page_len = [5, 16] KV lengths = [(2-1)×16+5, (1-1)×16+16] = [21,16]

plan 的工作量依赖请求组织；run 的工作量依赖实际 Q/KV 数据。一个 decode step 的 metadata 可服务多个具有相同布局的层，但不能因此把 KV 长度变化后的旧计划无限复用。若准备、更新、合并发生在 capture 外，Graph replay benchmark 不会自动把这些成本测进去。

旧 wrapper 的 fixed_split_size 只支持 Tensor Core decode；它改变分片计划，不等于跨 GPU 的 DCP。调用脚本会分别记录首次 plan 和热 plan，而不会把首次耗时直接命名为“纯编译时间”。

04计时边界，决定你到底优化什么

测量能说明什么不能偷换成什么
kernel activity / profiler单个 kernel 的执行区间，适合定位指令或访存瓶颈。多 kernel 操作的完整时间；简单累加可能重复计算重叠。
eager CUDA event span同一 stream 上 start 到 end 的跨度。GPU 吃空队列时，host 提交慢造成的空隙也可能在内。“CUDA events 总是排除 Python/host 成本”。
同步 wall time从调用前同步，到调用及调用后同步的耗时；可看到 host 与完成等待。纯 GPU 时间；它也包含同步自身成本。
Graph replay span固定图的重放成本，避免重复执行被 capture 的 Python 发射逻辑。完整服务的 ITL；capture 外的调度、计划与输入更新仍需另测。

源码中的具体机制：v2 的 eager 策略使用 events_no_delay；cuda_graph 策略实际捕获并重放。旧式 event 路径在计时 start 之前向 stream 发 delay kernel，让 CPU 有机会先排好后续任务；delay 本身在计时窗外，但它可以隐藏被研究的 host 提交瓶颈。反复采样无法补回被边界排除的成本。

05缓存的是“在什么条件下胜出的选择”

v2 把运行环境与操作身份分开：环境含 GPU/软件及测量策略；操作含 runner、形状桶和 layout/量化等 extras。相同形状并不自动意味着可以复用 winner。无验证钩子的 runner 仍按原有信任模型处理，不能声称每个 cache hit 都被语义验证。

跨 rank 一致性也是正确性问题：各 rank 独立计时会选出不同 tactic，某些 tactic 内部含 collective，选择分歧可能改变 collective 次序。该版本提供共享 store 下的 reload：框架在调优后执行 barrier，再让各 rank 清除本地 winner 并读取最后发布的共享结果。atomic rename 保证完整文件可见；它自身不保证所有 rank 的内存缓存已经一致。

自测：把 eager 调出的缓存拿去 Graph 部署，需要注意什么？

测量策略是 namespace 的一部分，应以同一 policy attach。即使输入 shape 相同，eager winner 也不必是 Graph winner。另需核对安装版本、GPU、布局、量化配置及 runner 验证能力。

06把读到的分支变成可执行实验

下载 decode 边界 benchmark。脚本以旧版公开 wrapper API 编写，比较 SIMT 与 Tensor Core 两个候选；先对稠密 FP32 reference 验证，再分别记录热 plan、eager 同步 wall、eager event span 与 Graph replay span。它不复现 Autotuner v2 的选 tactic 算法。

python bench-decode-boundaries.py --batch 4 --kv-len 4096   --page-size 16 --heads 32 --kv-heads 4 --head-dim 128   --dtype float16 --repeats 30 --inner 20 --output decode-b4-k4k.json

所有模式固定 use_cuda_graph=True 的 wrapper 元数据与预分配输出，保持计划条件一致；eager 表示用 Python 调 run，Graph 表示 replay。输入 buffer 复用，不做 L2 flush。结果记录版本、GPU、原始样本及误差；不支持的路径记为失败并以非零退出，失败不能当作性能样本。

扫什么为什么固定什么
batch：1 / 4 / 32；GQA：1 / 4 / 8看并行度与 Tensor Core 分组利用率如何改变选择。Q/KV dtype、head_dim、布局、页大小。
KV：512 / 4096 / 32768看 split-KV 收益和 merge 成本如何变化。记录 plan 与 run，不能只保留较快的一段。
eager / Graph / plan看 host 和图外成本是否改变结论。同输入、同输出分配；首次编译/调优/capture 独立记录。
