01MoE 的单位是 assignment，不只是 token

分析范围 · vLLM fused_experts_impl 的 aligned Triton 路径，BF16、标准 SwiGLU、无 bias、apply_router_weight_on_input=False。SGLang 和 FlashInfer 作为独立实现对照，不假定它们共享同一 kernel。

路由已经产生 topk_ids[T,k] 和 topk_weights[T,k]。每个 (token, slot) 是一个 assignment，展平编号 a=t×k+j。它不是 expert ID，也不是原 token ID。

X: [T,H] W13: [E,2I,H] W2: [E,H,I] G[a,:] = X[floor(a/k),:] × W13[expert(a)]ᵀ A[a,:] = SiLU(G[a,:I]) ⊙ G[a,I:] Y[a,:] = weight[a] × A[a,:] × W2[expert(a)]ᵀ O[t,:] = Σⱼ Y[t×k+j,:]
ROUTERtopk_ids + weightsALIGNsorted assignmentsGEMM₁gate + upACTIVATIONSiLU × upGEMM₂ + SUMweighted output

“fused MoE”这个名称不保证整个过程只有一次 launch。这里的源码明确依次调用第一 GEMM、激活、第二 GEMM 和 ops.moe_sum；量化时还包含相应转换步骤。

02用 8 个 assignment 算一遍 padding

T=4、k=2、E=4，路由为 [[0,2],[1,2],[0,3],[2,3]]。令 BLOCK_M=4，padding sentinel 为 T×k=8。下表展示一种按原 assignment 顺序排列的合法布局；同 expert 内部次序不要求固定。

expert真实 assignment IDs补齐后的块原 token IDs
00, 40, 4, 8, 80, 2, —, —
122, 8, 8, 81, —, —, —
21, 3, 61, 3, 6, 80, 1, 3, —
35, 75, 7, 8, 82, 3, —, —

expert_ids=[0,1,2,3] 按 M block 保存 expert，num_tokens_post_padded=16。8 个有效 assignment 占 16 个槽位，padding 比率 50%。这些补齐项会被 mask；但 tile 形状、调度与部分计算成本不会因此变成零。

nₑ = 分给 expert e 的真实 assignment 数 Pₑ = ceil(nₑ / BLOCK_M) × BLOCK_M padding fraction = (ΣPₑ − T×k) / ΣPₑ

此快照另有 naive 分支：当 expert_map is None 且 T×k×4 ≤ E 并满足量化条件时，可跳过排序，让一个 assignment 独占一个 M block。小 decode batch 下省去 align 成本可能更划算，尽管块的有效行数很低。

03两次 GEMM，相同 ID，不同除数

Triton 的一维 program ID 被映射为 (pid_m,pid_n)，以 GROUP_SIZE_M 分组顺序改善权重的 L2 复用。pid_m 选排序后的 M block，expert_ids[pid_m] 选该块权重，pid_n 选输出列块。

# 从源码简化的索引表达式；不是可直接运行的完整 kernel
a = sorted_token_ids[pid_m * BLOCK_M + arange(BLOCK_M)]
valid = a < T * k
expert = expert_ids[pid_m]
input_row = a // top_k_argument
A_ptr = base_A + input_row[:, None] * stride_am + offs_k[None, :] * stride_ak
C_ptr = base_C + a[:, None] * stride_cm + offs_n[None, :] * stride_cn

第一 GEMM 的 top_k_argument=k，所以 a=6 读取原 token 3。输出写回 assignment 6 的位置，而不是排序表的第几行。激活后的张量已是 [T×k,I]，第二 GEMM 传入 top_k_argument=1，a=6 读取中间结果第 6 行。这是最容易把正确形状写成错误数值的地方。

路由权重在第二 GEMM 的 FP32 accumulator 上相乘，之后才 cast 到输出 dtype，最后按 token 合并 k 份输出。若某路径将权重作用在激活之前，必须依据模型定义判断；非线性存在时，一般不能把这个权重随意从前移到后。

expert_map 标记当前 EP rank 没有的 expert 时，kernel 可写零；这不能替代真正的跨卡 dispatch。sorted_token_ids 表示一种 gather/scatter 索引协议，并不要求先把输入 X 的每个 assignment 物理复制到连续数组。

检查理解 · 如果第二个 GEMM 也除以 k，会发生什么？

它会把不同 assignment 的激活行折叠到同一行：例如 k=2 时 a=6 错读第 3 行。输出形状仍可能合法，因此必须用具有可区分 token/expert 数据的 reference 校验。

04把 padding、负载不均衡和流量分开看

Assignment → expert blocks

CPU / 确定性路由示例

计算器固定 H=4096、I=14336、BF16，统计量是教学模型。两次 GEMM 有效 FLOPs 为 6×T×k×H×I；把 T×k 替换为 ΣPₑ 得到按行补齐的名义工作量，实际指令量还受列块、K 尾块与实现影响。

第一 GEMM 输出、激活输出、第二 GEMM 输出都物化时，仅它们的最低写入量就是 T×k×(2I+I+H)×2 B。读回、量化 scales、padding 和原输入/权重流量还没有计入。集中路由可能减少 padding，却增大某 expert 的负载和 EP 尾部延迟；低 padding 不等于最优负载。

05SGLang 与 FlashInfer：边界不同，不能只换名字

SGLang：up/down 可以使用不同配置

该快照的 Triton 路径会分别取得 up 与 down 配置。TMA 需要硬件支持且调优配置显式包含 USE_TMA=true，不能因为 GPU 是 Blackwell 就推断启用。第二 GEMM 还可能直接写最终输出、融合 sum/all-reduce、或者 no_combine 留给后续处理；判断中间张量流量前要先读这些分支。

FlashInfer：grouped FP8 的输入契约已经变了

对照 CutlassFP8GroupwiseScaledGroupGEMMSM100：这是一项 grouped GEMM primitive，本页不把它直接等同于 cutlass_fused_moe 的内部调用。这里 A 已按 group 连续排列，m_indptr 描述各 group 的边界。它没有 vLLM 那样的 a//k gather 语义，routing、permute 与最终 unpermute/combine 是调用者需要解决的事情。

构建项源码中的具体选择含义
problem / pointersMᵢ=m_indptr[i+1]−m_indptr[i]；Aᵢ=A+offset×K；Bᵢ=B+i×N×K每个 group 可有不同 M，共享 N/K；B 是按 expert 分组的 [N,K] 存储。
matrix layoutA RowMajor、B ColumnMajor、D RowMajor；FP32 accumulatorB 的数学视图为 [K,N]，不要因为其存储按 [N,K] 排列就再转置一次。
tile / clusterMMA tile=(MmaSM×128,128,128)，cluster=(MmaSM,1,1)1SM/2SM 改变协作粒度；小 expert 的 M 可能无法有效利用更大 tile。
stage countStageCountAutoCarveout<sizeof(Epilogue::SharedStorage)>mainloop stage 要给 epilogue 留 SMEM；不是固定写死的 stages=3。
scale layoutScaleMajorK 决定 SFA 的布局与 offset；SFB 按 group、sf_n、sf_k 偏移scale 的粒度和内存布局都是接口契约，不能只保证 FP8 数据本身形状对。

例如 m_indptr=[0,128,384]，N=K=256，scale granularity=(1,128,128)、ScaleMajorK=true：group 1 的 M=256，A 偏移=128×256=32768 个 FP8 元素，B 偏移=65536 个元素，SFA 偏移=128×2=256 个 float scale，SFB 偏移=1×2×2=4 个 scale。换成 MN-major scale，指针与 stride 规则都要重算。

06MoE 的优化目标是整条链

测试轴为什么要扫需要记录
T=1/16/256/4096，k=1/2/8decode 小矩阵与 prefill 大矩阵的瓶颈不同。实际 backend、align/permute、GEMM₁、激活、GEMM₂、combine 各段耗时。
均衡 / 热点 / 空 expert平均 M 掩盖 padding、尾部和专家不均衡。每 expert 的真实/补齐 M，最大值与分位数。
BF16 / FP8 / FP4 与不同 scale layout低比特可降低权重流量，也引入转换和 scale 读取。误差、转换成本、量化 workspace；必须比较相同模型语义。
单卡 / EP / TP+EPGEMM 更快可能只是把瓶颈移到通信。端到端 token 延迟，通信与 GEMM 重叠、SM 竞争、rank 尾部。

本页验证脚本用小矩阵的逐 token/expert reference 对照分块 gather/scatter 实现，覆盖 k=1/2/4、尾部 padding 和热点。它验证索引与数学，不证明 GPU kernel 的精度或性能。
