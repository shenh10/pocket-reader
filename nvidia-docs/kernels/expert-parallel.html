01路由到 expert，通信却先看 rank

分析范围 · DeepEP EPv2 的 ElasticBuffer 与 NCCL Gin 路径。device 细读以非 hybrid 的 dispatch_impl 为主；多 scale-out 域会选 hybrid_dispatch_impl。V1 的 Buffer/NVSHMEM API 不属于本页。

一个 token 的 top-k experts 可以落在同一个 rank。dispatch 发送输入激活时，可先对目的 rank 去重：一个 rank 收到一次 X，就能供本地多个 expert 使用。这不会减少 expert GEMM 的 assignment 数，只减少相同输入的逻辑传输副本。

取 E=8、4 个 rank、每 rank 连续拥有 2 个 expert。源 rank 0 的一个 token 命中 [0,1,4,5]：4 个 assignment，对应 rank [0,0,2,2]，去重后只有 {0,2}。其中 0 是本地，真正离开源 rank 的激活副本只有 1 份。

02Handle 保存的是反向路由所需的信息

状态作用错误后果
topk_idx / do_expand保存路由与是否按 expert 展开。non-expand 按 rank 接收；expand 为每个 expert/token 分配 slot。拿 non-expand 的“接收 token 数”当作 GEMM assignment 数，会漏算同 rank 多 expert。
psum_num_recv_tokens_per_scaleup_rank去重后的接收数量前缀和；同 token 对同 rank 计一次。按 k 倍估计所有 rank 流量会高估；忽略热点则会低估尾部。
psum_num_recv_tokens_per_expert按 expert_alignment 补齐的局部 expert 边界；expand 的前缀语义有特殊定义。把普通 inclusive prefix 的差值直接用于 expand 模式，可能把 padding 当真实行。
dst_buffer_slot_idx / source metadata记录发送目的 slot 与源 token 索引，combine 用它逆转路由。重新采样 top-k 后复用旧 handle，会把结果送回错误位置。
EventOverlap / tensor ownership记录通信完成与跨 stream 使用期间的对象寿命。CPU 返回不代表 GPU 完成；过早消费或释放产生竞争。

cached handle 只适用于路由布局仍相同的重放；API 要求此时 topk_idx 与 topk_weights 参数为 None。没有必要每次重算的 metadata 可以复用，但下一批 token 内容相似并不能证明它拥有同一份路由。

03真正的数据路径：TMA、去重、slot、传输完成

host 端按拓扑构造 JIT 参数，选择 dispatch 或 hybrid_dispatch。下面逐步对应 non-hybrid device 文件中的 token 循环。

阶段源码行为完成 / 复用边界
搬入输入TMA 将 hidden 向量加载到 warp 对应的 SMEM buffer；FP8 scale 用相应 copy 路径。复用 buffer 前等待前一次 TMA store；加载后通过 mbarrier 的 transaction 与 phase 等待。
附加路由各 lane 读取 top-k index/weight，写入 source rank/token metadata。SMEM 数据发布前执行 tma_store_fence；不能在发布后继续无同步改写。
rank 去重expert_id / experts_per_rank 得到 rank；deduplicate 后 atomicAdd 分配目的 slot。同一个目的 rank 只有一个代表 lane 分配 slot；cached 模式复用已有索引。
发送可经对端可达地址执行 TMA store；不可直接访问时先落到 send buffer，再 gin.put。RDMA put 使用 send buffer 前必须等 TMA store 完成；仅发出 put 不意味着远端可消费。
全局完成token 循环后进入 gpu_barrier 的通信完成协议。接收方进入后续消费前需要真实的到达保证；单个 CTA 的 __syncthreads 不覆盖网络。

它的优化不是简单调用一个 all-to-all：布局、去重、slot 分配、源标记和搬运协议共同构成通信 kernel。hybrid 模式还分 scale-out 与 scale-up 转发；不能用上面单域的步数推导多节点 NIC 流量。

04一个流量数，至少要说明三种口径

目的 rank 去重

单个源 token / 激活 payload 模型

此模型的 distinct_remote_ranks × H × bytes 仅表示离开源 rank 的一次 dispatch 激活 payload 下界。没有计算 top-k metadata、FP8 scales、协议包、对齐、重传、NVLink↔RDMA 转发、combine 返回流量或内存 staging。它不是 NIC wire bytes，也不是 DeepEP benchmark 的“逻辑带宽”。

combine 时同 rank 的多个 expert 结果可先局部归约，再向源 rank 返回；reduce 顺序、expand 模式、bias 和精度都会影响结果。CPU 理想模型里，先局部求和再跨 rank 求和与直接求和等价；BF16 下不同顺序通常不保证 bitwise 一致。

05能重叠的是独立工作，依赖工作仍要等

async_with_compute_stream=True 的含义是当前计算流不会自动等通信结束。返回的 event 要在真正消费 recv_x 前建立等待；设置异步参数本身没有消除数据依赖。

# 生命周期示意；需先按对应版本初始化 buffer 与输入
recv_x, recv_idx, recv_w, handle, done = buffer.dispatch(
    x, topk_idx=ids, topk_weights=weights, num_experts=E,
    async_with_compute_stream=True,
)
independent_work()             # 不能读 recv_x，也不能改写在途输入
done.current_stream_wait()     # 在当前 CUDA stream 上插入依赖
expert_output = local_moe(recv_x, recv_idx, recv_w, handle)
out, _, combined = buffer.combine(
    expert_output, handle, async_with_compute_stream=True,
)
other_independent_work()
combined.current_stream_wait()
consume(out)

local_moe 是占位接口：它必须匹配 handle 的 expand/non-expand 布局，明确路由权重在哪里乘且只乘一次。不能将上一页 Triton 返回的 tensor 无条件塞进这里。若传 previous_event，接口还要求 allocate_on_comm_stream；要同时满足数据依赖和 allocator 生命周期。

with EventOverlap 在退出作用域时才 wait，因此 with 块内应放可重叠的独立工作，不应误以为进入 with 就已经等待。跨流复用输入或 workspace 时，要确保所有使用者都已完成再释放。

检查理解 · 为什么 dispatch 更快，整层 MoE 仍可能更慢？

通信 kernel 可能抢占 GEMM 所需 SM、内存带宽或缓存资源。也可能优化了平均吞吐，但热点 rank 的 combine 尾部更长。要量整层 critical path，而不是只比较孤立 dispatch 的带宽。
